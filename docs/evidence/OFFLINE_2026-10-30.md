# Draft and offline reliability — 30 October 2026

v0.8 implements the first SY-03 slice. It does not complete the full offline/device or production release gates.

## Draft ownership and recovery

A separate IndexedDB record stores unsubmitted board hits and keypad total/dart-count/double details. A tab identifier lives in sessionStorage; drafts are not shared between independent tabs. Duplicate tabs that inherit an identifier use compare-and-swap tokens to reject competing draft writes. Records expire after seven days. Closing a tab may discard its identifier; recorded match data remains in the main database.

The draft holds the complete normalised match/command prefix and saved workspace revision. Refresh offers explicit restore/discard only for the exact saved turn. A new match, changed command history, completed leg, bot turn or recorded-then-undone visit cannot silently receive an old draft. Draft validation rejects invalid hit sequences and unsupported formats. Editable keypad totals remain unsubmitted even when impossible; normal scoring validation runs on recording.

A separate draft status reports save failures. Draft writes do not alter result history or workspace revision, and are queued; an older completed save cannot mark a newer pending edit saved. Navigation and input-method changes retain draft state. Exported backups intentionally contain recorded matches/profiles, not tab drafts.

## Offline shell and update policy

Production builds generate a service worker whose cache identity derives from emitted assets, public install assets and worker source. Installation precaches the complete public shell, including the import-review worker. A failed asset download aborts the new installation; the existing worker remains active. No match data, API requests, credentials, external resources or media enter this cache.

An active worker serves its own version of the shell and assets. Updates wait for all app tabs to close; the application does not call skipWaiting or force a reload. Activation removes only obsolete Darts Master shell caches, preserving unrelated caches. This requires an HTTPS or trusted localhost origin and root-path hosting. Development mode does not register a worker.

Install metadata includes a provisional title, vector target and 192/512 PNG icons. A browser-provided install prompt is offered when available. Installation and storage retention remain browser controlled; no native-app or cloud-resilience claim is made.

## Evidence

- Six draft unit cases cover tab isolation, duplicate-tab conflict, exact-history identity, invalid input, expiry, and recorded-then-undone invalidation.
- Four development-browser workflows cover board/keypad restore, discard, navigation, correction and write failure.
- Five production-browser workflows use the generated worker and built assets: phone-sized disconnected reopen/scoring/backup; waiting multi-tab updates; interrupted install and retry; cache boundaries/API bypass; failed first-install readiness.
- Fresh Chromium visual checks at 1366 and 390 CSS pixels show the recovery prompt without horizontal overflow.

The production test server’s release switches are test-only fixtures outside the emitted app; its assertions exercise browser service-worker lifecycle, not mocked offline hooks.

Local validation for this increment: TypeScript and production build pass, with 93 unit tests, 37 development-browser tests and five production offline/update tests.

## Remaining gates

Real Dell/phone/tablet installed-app sessions, Safari/Firefox coverage, installation prompts, operating-system suspension/tab restoration, storage pressure/eviction and hosted cache-header/deployment checks remain. A draft can be lost if its pending write has not finished or its tab identifier is discarded. Browser data clearing removes both offline assets and local saves. Keep a downloaded backup separately. Future online-only features need explicit offline/retry states; they do not exist yet.

Lifecycle design follows [MDN’s service-worker guidance](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) and [Chrome’s update lifecycle guidance](https://developer.chrome.com/docs/workbox/service-worker-lifecycle).
